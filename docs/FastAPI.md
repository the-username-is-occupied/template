## Общая схема

Сервис управляет пулом технических Google-аккаунтов и предоставляет
пользователям доступ к NotebookLM через обёртку `notebooklm-py`.

**Laravel** — основной API: аутентификация пользователей, бизнес-логика,
управление аккаунтами, захват аккаунтов из пула, диспетчеризация задач.

**FastAPI** — тонкий stateless исполнитель. Держит пул инициализированных
`NotebookLMClient` в памяти, маршрутизирует входящие запросы по `account_id`,
не принимает никаких решений о том, какой аккаунт использовать.

**Redis** — блокировки аккаунтов, очереди асинхронных задач, pub/sub для SSE.

**Postgres** — persistant аккаунты

## Общее
- Все ответы содержат время выполнения запроса
- Общей hendler ошибок. перехватывает все ошибки и отвечает с кодом и сообщением ошибки
- Request log - логируем все запросы пользователей

## Логирование запросов
- Добавить middlware для добавление запросу сквозного id
- Сохранять время запроса (успешность запроса, полное, внутри laravel сервиса, внутри fast api и других сервисов)
- Успешность запросов для ask считается как успешность ответа. Так как пользователь платит деньги за запрос, успешным считается только тот на который предоставлен ответ (содержание ответа от notebooklm не имеет значение)

## Тестирование
- Общей тест в laravel для всех эндпоинтов fastapi. Без фейков. Только ручной запуск
- Необходимо протестироват конкурентные ask запросы к одному блокноту

## Пул аккаунтов и захват (Laravel)

Вся логика захвата аккаунтов живёт в Laravel, а не в FastAPI.
Laravel знает про аккаунты, пользователей, лимиты и состояние.
FastAPI получает уже выбранный `account_id` и просто использует
соответствующий клиент из своей памяти.

Захват — атомарный `SET NX EX` в Redis. Если все аккаунты заняты — 503.

## FastAPI: модель конкурентности

FastAPI работает на **одном uvicorn процессе** с одним asyncio event loop.
Несколько workers не нужны и вредны: каждый worker создаёт свой пул
клиентов, что порождает race conditions при записи cookie-файлов.

Конкурентность обеспечивается asyncio: пока один запрос ждёт ответа от
Google (~1–5 с), event loop обслуживает остальные запросы.

`notebooklm-py` клиент является **async re-entrant** — параллельные вызовы
с разными параметрами технически допустимы. Однако если два параллельных
запроса одновременно триггернут refresh токена, один из них получит лишний
retry. Это обрабатывается библиотекой прозрачно, но создаёт ненужный шум.

**Типы блокировок:**

- `ask` — не требует эксклюзивного лока. Параллельные ask на одном
аккаунте допустимы. Redis-счётчик `ask_count` используется только для
метрик и backpressure

**Масштабирование:** единица масштабирования — количество аккаунтов,
не количество воркеров. Один процесс с 20 аккаунтами обслуживает
~260 ask-запросов в минуту.

## Масштабирование ask через shared notebook

Один ноутбук можно расшарить на несколько технических аккаунтов (viewer).
Это позволяет распределить нагрузку: 100 пользователей × 1 ноутбук →
10 аккаунтов × 10 пользователей на аккаунт.

Sticky-назначение пользователя к аккаунту при этом **не требуется**,
потому что контекст разговора хранится на нашей стороне (см. ниже).

## Управление сессиями Google (auth lifecycle)

Ключевые факты из `auth-cookie-lifecycle.md`:

**`__Secure-1PSIDTS`** — главный auth-куки с рекомендуемым каденсом
ротации ~600 секунд. Без ротации сессия начинает падать через несколько
часов. Эмпирически замороженный `*PSIDTS` продолжал работать 32+ часа
на стабильном IP, но в datacenter-окружении деградация наступает быстрее.

**Критично:** чистый RPC-трафик к `notebooklm.google.com` не триггерит
ротацию токена. Ротация происходит только при обращении к identity-поверхности
Google. Без явного keepalive сессия молча деградирует.

**Обязательно использовать `keepalive=600`** при инициализации каждого
клиента. Это запускает фоновую задачу которая периодически ротирует
`*PSIDTS` через `accounts.google.com/RotateCookies`.

**Три throttle-гарда** в библиотеке предотвращают флуд RotateCookies:
mtime быстрый путь (60 с), in-process asyncio lock, cross-process flock.
Для нашего случая (один процесс, изолированные storage paths) они
работают корректно из коробки.

Один shared volume cookies_data монтируется и в Laravel и в FastAPI. Laravel получает storage_state.json от администратора, пишет его на диск по пути /{account_uuid}/storage_state.json. Потом вызывает FastAPI POST /accounts — FastAPI читает файл с диска, инициализирует клиент с keepalive=600, добавляет в _clients. Никакого рестарта.
Дальше keepalive сам обновляет этот файл по мере ротации токенов. Laravel его больше не трогает.
yaml# docker-compose.yml
services:
  app:
    volumes:
      - cookies_data:/cookies   # Laravel пишет сюда при добавлении аккаунта

  fastapi:
    volumes:
      - cookies_data:/cookies   # FastAPI читает отсюда и обновляет (keepalive)

volumes:
  cookies_data:                 # один volume, оба сервиса видят одно и то же

Жизненный цикл добавления аккаунта
Админ загружает storage_state.json через Laravel UI
        ↓
Laravel: валидировать файл (проверить наличие SID, __Secure-1PSIDTS)
        ↓
Laravel: сохранить запись в google_accounts (id, name, pool, status=initializing)
        ↓
Laravel: записать файл → /cookies/{account_id}/storage_state.json
        ↓
Laravel: POST /accounts на FastAPI {account_id, cookie_path, pool}
        ↓
FastAPI: NotebookLMClient.from_storage(path, keepalive=600).__aenter__()
        ↓
FastAPI: добавить в _clients[account_id]
        ↓
FastAPI: ответить 201 Created
        ↓
Laravel: обновить статус → active

Старт FastAPI после рестарта
При рестарте контейнера FastAPI не знает что было в памяти. Поэтому при старте он запрашивает все активные аккаунты из Postgres и инициализирует клиентов из файлов которые уже лежат на shared volume — они никуда не делись.
FastAPI startup:
  для каждого → from_storage(account.cookie_path, keepalive=600)
Файлы на volume персистентны между рестартами — keepalive постоянно их обновляет, поэтому после рестарта клиенты стартуют с уже свежими токенами.

Удаление аккаунта
Laravel: UPDATE google_accounts SET status = 'inactive'
        ↓
Laravel: DELETE /accounts/{account_id} на FastAPI
        ↓
FastAPI: client.__aexit__(), убрать из _clients
        ↓
Laravel: опционально удалить файл с диска

**Мониторинг здоровья сессий:** `mtime` cookie-файла — единственный
надёжный индикатор свежести. `*PSIDTS` хранится без `expires`, поэтому
метаданные куки бесполезны. FastAPI предоставляет `/health/accounts`
endpoint, Laravel поллит его и помечает деградировавшие аккаунты.

**`NOTEBOOKLM_REFRESH_CMD`:** реактивный рычаг восстановления. Запускается
библиотекой при 401. Должен уведомлять Laravel и по возможности
делать re-extract через Firefox.

**DBSC (Device-Bound Session Credentials):** долгосрочная угроза.
По состоянию на май 2026 применяется только к Chrome-клиентам.
Non-Chrome HTTP клиенты (httpx, наш FastAPI) пока не затронуты.
Когда Google распространит DBSC на non-Chrome пути — L1/L2/L3 сломаются.
Escape: CDP-attach к запущенному Chrome (L5) или CookieCloud (L6).

## Управление источниками и загрузка MD-бандлов

### Загрузка MD-бандлов через Shared Volume
Чтобы избежать оверхеда на передачу файлов по HTTP, загрузка MD-бандлов в NLM реализована через Docker volume.

1. В `docker-compose.yml` монтируется общий volume `bundles_data` для Laravel и FastAPI.
2. Laravel компилирует MD-файл и сохраняет его на диск в этот volume (например, `/bundles/{bundle_id}.md`).
3. Laravel вызывает FastAPI эндпоинт загрузки источника, передавая только `file_path` (путь внутри контейнера)
4. FastAPI читает файл локально с диска и загружает его в NLM.

### Пакетное извлечение транскриптов YouTube (Temporary Extraction Notebook)
Для YouTube-источников мы используем NLM как "черный ящик" для извлечения текста. Чтобы не превышать лимит в 50 источников, используется выделенный временный блокнот и пакетная загрузка.

1. Laravel вызывает `POST /internal/youtube/extract-batch`, передавая массив `video_urls` и `account_id`.
2. FastAPI получает/создает Temporary Extraction Notebook.
3. FastAPI пакетно добавляет URL во временный блокнот.
4. FastAPI извлекает транскрипты и формирует мапу `{url: text}`.
5. **Критически важно:** FastAPI немедленно удаляет эти URL из временного блокнота, освобождая слоты для следующих пачек.
6. FastAPI возвращает мапу с транскриптами в Laravel.

### Асинхронный парсинг Telegram (Batched Webhooks)
Парсинг больших каналов занимает много времени, поэтому используется асинхронная модель с вебхуками.

1. Laravel вызывает `POST /internal/telegram/parse/initiate`, передавая `channel_url` и `webhook_url`.
2. FastAPI начинает парсинг и сразу возвращает `202 Accepted`.
3. По мере парсинга FastAPI накапливает посты пачками (batch_size = 100-500).
4. FastAPI отправляет `POST {webhook_url}` в Laravel с JSON-массивом постов.
5. Laravel сохраняет пачку и отвечает `200 OK`.

## Риски и ограничения

| Риск | Вероятность | Митигация |
|---|---|---|
| Google risk-scoring при datacenter IP | Средняя | Residential proxy, постепенный прогрев аккаунтов |
| Протухание сессии | Низкая при keepalive=600 | Мониторинг mtime, REFRESH\_CMD |
| DBSC rollout на non-Chrome | Отложенная | Следить за Chrome release notes, готовить L4/L5 |
| Rate limit на аккаунт | Средняя | Heavy-пул, очереди, throttle по аккаунту |
| Re-auth после смены пароля | Ручная | Алерт из REFRESH\_CMD, ручная повторная авторизация |
