# NotebookLM Multi-Tenant Service — Архитектурные решения

## Стек

Laravel · Redis · Postgres · FastAPI · Docker Compose

---

## Общая схема

Сервис управляет пулом технических Google-аккаунтов и предоставляет
пользователям доступ к NotebookLM через обёртку `notebooklm-py`.

**Laravel** — основной API: аутентификация пользователей, бизнес-логика,
управление аккаунтами, захват аккаунтов из пула, диспетчеризация задач.

**FastAPI** — тонкий stateless исполнитель. Держит пул инициализированных
`NotebookLMClient` в памяти, маршрутизирует входящие запросы по `account_id`,
не принимает никаких решений о том, какой аккаунт использовать.

**Redis** — блокировки аккаунтов, очереди асинхронных задач, pub/sub для SSE.

**Postgres** — пользователи, аккаунты, задания, история сообщений.

---

## Пул аккаунтов и захват (Laravel)

Вся логика захвата аккаунтов живёт в Laravel, а не в FastAPI.
Laravel знает про аккаунты, пользователей, лимиты и состояние.
FastAPI получает уже выбранный `account_id` и просто использует
соответствующий клиент из своей памяти.

Захват — атомарный `SET NX EX` в Redis. Если все аккаунты заняты — 503.

**Два пула с разным назначением:**

- **ask-пул** (~70% аккаунтов) — только быстрые операции: ask, list, get metadata
- **heavy-пул** (~30% аккаунтов) — медленные операции: add\_source, generate\_audio, generate\_video

Пропорция настраивается в Postgres. Перевод аккаунта между пулами —
изменение одного поля + рестарт FastAPI.

**Фолбэк:** если ask-пул полностью занят, Laravel может временно взять
аккаунт из heavy-пула при условии что на нём нет активной heavy-операции.

## Синхронные vs асинхронные операции

**Синхронный прямой HTTP-вызов** (Laravel → FastAPI → ответ):

| Операция | Таймаут |
|---|---|
| ask, chat | 30–60 с |
| list\_notebooks, create\_notebook | 10 с |
| add\_source\_url | 60 с |

**Асинхронные через Job + SSE** (только для операций занимающих минуты):

| Операция | Таймаут |
|---|---|
| generate\_audio | 10 мин |
| generate\_video | 15 мин |
| generate\_quiz | 5 мин |

Для async-операций Laravel диспетчеризует Job, возвращает `job_id`.
Клиент подписывается на SSE-эндпоинт и получает статус через Redis pub/sub.

## FastAPI: модель конкурентности

FastAPI работает на **одном uvicorn процессе** с одним asyncio event loop.
Несколько workers не нужны и вредны: каждый worker создаёт свой пул
клиентов, что порождает race conditions при записи cookie-файлов.

Конкурентность обеспечивается asyncio: пока один запрос ждёт ответа от
Google (~1–5 с), event loop обслуживает остальные запросы.

`notebooklm-py` клиент является **async re-entrant** — параллельные вызовы
с разными параметрами технически допустимы. Однако если два параллельных
запроса одновременно триггернут refresh токена, один из них получит лишний
retry. Это обрабатывается библиотекой прозрачно, но создаёт ненужный шум.

**Типы блокировок:**

- `ask` — не требует эксклюзивного лока. Параллельные ask на одном
аккаунте допустимы. Redis-счётчик `ask_count` используется только для
метрик и backpressure.
- `heavy_lock` — эксклюзивный лок на аккаунт. Ask не идёт пока активна
heavy-операция; heavy-операция не стартует пока есть активные ask.

**Масштабирование:** единица масштабирования — количество аккаунтов,
не количество воркеров. Один процесс с 20 аккаунтами обслуживает
~260 ask-запросов в минуту.

## Масштабирование ask через shared notebook

Один ноутбук можно расшарить на несколько технических аккаунтов (viewer).
Это позволяет распределить нагрузку: 100 пользователей × 1 ноутбук →
10 аккаунтов × 10 пользователей на аккаунт.

Sticky-назначение пользователя к аккаунту при этом **не требуется**,
потому что контекст разговора хранится на нашей стороне (см. ниже).

## История сообщений и контекст чата

**Проблема:** в NotebookLM нет множественных чатов. На сервере Google
существует одна активная цепочка на пару account+notebook. `conversation_id`
в API — идентификатор текущего треда, а не механизм изоляции разговоров.
Если несколько пользователей шлют запросы через один аккаунт, они
пишут в один и тот же тред и интерферируют друг с другом.

**Решение:** каждый `ask()` — самодостаточный запрос. `conversation_id`
не используется. История хранится в Postgres (таблица `nlm_messages`).
При каждом запросе Laravel достаёт последние N сообщений пользователя
для данного ноутбука и передаёт их в FastAPI как контекст, который
инжектируется в текст вопроса.

**Следствие:** пользователи полностью изолированы друг от друга даже
при совместном использовании одного аккаунта. Sticky-назначение
не влияет на корректность — только на равномерность нагрузки.

## Управление сессиями Google (auth lifecycle)

Ключевые факты из `auth-cookie-lifecycle.md`:

**`__Secure-1PSIDTS`** — главный auth-куки с рекомендуемым каденсом
ротации ~600 секунд. Без ротации сессия начинает падать через несколько
часов. Эмпирически замороженный `*PSIDTS` продолжал работать 32+ часа
на стабильном IP, но в datacenter-окружении деградация наступает быстрее.

**Критично:** чистый RPC-трафик к `notebooklm.google.com` не триггерит
ротацию токена. Ротация происходит только при обращении к identity-поверхности
Google. Без явного keepalive сессия молча деградирует.

**Обязательно использовать `keepalive=600`** при инициализации каждого
клиента. Это запускает фоновую задачу которая периодически ротирует
`*PSIDTS` через `accounts.google.com/RotateCookies`.

**Три throttle-гарда** в библиотеке предотвращают флуд RotateCookies:
mtime быстрый путь (60 с), in-process asyncio lock, cross-process flock.
Для нашего случая (один процесс, изолированные storage paths) они
работают корректно из коробки.

**Хранение cookie-файлов:** каждый аккаунт — изолированный path
(`/cookies/acc1`, `/cookies/acc2`). Docker volume per account.
Никогда не читать один storage из двух процессов одновременно.

**Первичная авторизация:** через Firefox (`--browser-cookies firefox`).
Firefox не имеет App-Bound Encryption в отличие от Chrome 127+,
поэтому cookies читаются без admin-привилегий. Рекомендуемый путь
для unattended-сценариев.

**Мониторинг здоровья сессий:** `mtime` cookie-файла — единственный
надёжный индикатор свежести. `*PSIDTS` хранится без `expires`, поэтому
метаданные куки бесполезны. FastAPI предоставляет `/health/accounts`
endpoint, Laravel поллит его и помечает деградировавшие аккаунты.

**`NOTEBOOKLM_REFRESH_CMD`:** реактивный рычаг восстановления. Запускается
библиотекой при 401. Должен уведомлять Laravel и по возможности
делать re-extract через Firefox.

**DBSC (Device-Bound Session Credentials):** долгосрочная угроза.
По состоянию на май 2026 применяется только к Chrome-клиентам.
Non-Chrome HTTP клиенты (httpx, наш FastAPI) пока не затронуты.
Когда Google распространит DBSC на non-Chrome пути — L1/L2/L3 сломаются.
Escape: CDP-attach к запущенному Chrome (L5) или CookieCloud (L6).

## Таблица Postgres: ключевые сущности

| Таблица | Назначение |
|---|---|
| `google_accounts` | Технические аккаунты: pool type, status, health, last\_used\_at |
| `nlm_jobs` | Async задания: статус, результат, account\_id |
| `nlm_messages` | История чатов: user\_id, notebook\_id, question, answer |
| `user_notebook_assignments` | Опциональный sticky routing (для балансировки нагрузки) |

## Добавление нового аккаунта

1. Авторизовать в Firefox, извлечь cookies через `notebooklm login --browser-cookies firefox`
2. Скопировать `storage_state.json` в изолированный volume
3. Добавить запись в `google_accounts` с указанием пула и пути к cookies
4. Рестарт FastAPI-контейнера (или вызов `/accounts` POST endpoint если реализован hot-add)
5. Расшарить нужные ноутбуки на новый аккаунт через NotebookLM UI

## Риски и ограничения

| Риск | Вероятность | Митигация |
|---|---|---|
| Google risk-scoring при datacenter IP | Средняя | Residential proxy, постепенный прогрев аккаунтов |
| Протухание сессии | Низкая при keepalive=600 | Мониторинг mtime, REFRESH\_CMD |
| DBSC rollout на non-Chrome | Отложенная | Следить за Chrome release notes, готовить L4/L5 |
| Rate limit на аккаунт | Средняя | Heavy-пул, очереди, throttle по аккаунту |
| Re-auth после смены пароля | Ручная | Алерт из REFRESH\_CMD, ручная повторная авторизация |
